# 判断の記録

## 2026-10-17 始めたときの仮決定

- **Windows の常駐は C++ / Win32 / Direct2D、設定画面は別プロセスの WinUI 3**: 本人の「無用にリソースを消費しない」と「ネイティブ UI で描画」を両立させるため。WinUI 3 や .NET を常駐側に入れると、絵が小さくても数十MBを持ち続ける。設定画面は開いている間だけなので WinUI 3 にした
- **Mac は Swift の1つのアプリ**: SwiftUI / AppKit は常駐させても軽く、分ける利点が薄い
- **OS の画像の仕組み（WIC・ImageIO）で読む**: 自前の GIF の読み込みや共通のライブラリを持たない。2つの OS で共有するのは設定の JSON の形と `SPEC.md` だけ
- **通知領域・メニューバーのアイコンも既定で出さない**: 本人の「アイコンが出っぱなしにならない」を強めに取った。設定画面はもう一度起動すると開く。出したい場合は設定で出せる。本人に確認する
- **名前は pixwall（仮）**

## 2026-10-17 解像度の変化とメニューバーの下

- **解像度が変わったら自動で合わせる**: 本人は解像度をよく変える。OS が変化を知らせてくれるので、そのときだけ計算し直せば重くならない。見張り続ける方法は取らない。自動で合わないときのために、手で「表示を更新」もできるようにする（本人の要望）
- **倍率は物理ピクセルで計算する**: 拡大率が変わったときにドットの大きさが不ぞろいになったり、ぼやけたりしないため
- **Mac はメニューバーの下も、Windows はタスクバーの下も描く**: 本人の要望。ほかのアプリはメニューバーの下が描かれず、半透明・透明なメニューバーだと浮いて見える。原因はたぶん `visibleFrame` を使っていることか、`NSWindow` が自分で位置を直すこと。`frame` を使い、`constrainFrameRect` を上書きする

## 2026-10-17 Mac 版の最小の形

- **Xcode のプロジェクトを持たず SwiftPM にした**: `.xcodeproj` は差分が読みにくく、Linux 側で書いて Mac でビルドする流れに向かない。`.app` は `build-app.sh` で包む。`Info.plist` の `LSUIElement` に加え、コードでも `setActivationPolicy(.accessory)` にして、`.app` にせず動かしたときも Dock に出さない
- **画面ごとに窓とタイマーを1つずつ持つ**: 今は全画面に同じ画像だが、後で画面ごとに別の画像・別の止める条件（隠れているか）になるため。フレームの `CGImage` は窓どうしで共有する
- **MacBook Air M1（macOS 27、Xcode 27 beta 2）で確かめたこと**: 64×64・30フレーム・100ms の GIF を「整数倍で最大」で1画面に出して、CPU 0.0〜0.3%、メモリ 9.5MB（`top` の MEM）。目安（0.5% 未満・30MB 未満）に収まる。メニューバーの下・Dock の下まで描け、ウィジェットとアイコンは手前に出る。Dock にアイコンは出ない
- **まだ確かめていないこと**: ほかの窓で全部隠れたときに止まるか（`occlusionState` がデスクトップの高さの窓でも変わるか）、画面の消灯・ロック・低電力モードで止まるか、解像度を変えたときの作り直し、Mission Control・操作スペースの切り替え
- **`.app` を `~/Documents` の中から起動すると「書類フォルダへのアクセス」の許可を求められた**: 画像は `~/Library/Application Support/pixwall/` に置いていても出た。`.app` を `~/Applications` に置いて起動すると出ない（1回目の画面は残っていたので、2回目以降に出なかったかは画面だけでは言い切れない）。試すときは `~/Applications` に置く

## 2026-10-18 Windows 版の最小の形（to-fu で未確認）

- to-fu を操作する道具がつながらなかったので、コードと単体テストまで進めた。Win32 の部分は Linux ではビルドできず、まだ一度もコンパイルしていない
- **OS に触らない計算を `windows/core/` の C++ に分け、Linux の g++ でも単体テストする**: Windows に触れない間も確かめられるように。並べ方・待ち時間は Mac 版と同じ値になるテストにした
- **GIF の重ね方は自前で当てる**: WIC は GIF のフレームを重ねずに返す（Mac の ImageIO は重ねて返す）。`Background` はブラウザと同じく透明に戻す
- **まずは `ID2D1HwndRenderTarget` で描く**: DESIGN では DXGI のフリップモデルにしていたが、WorkerW（ほかのプロセスの窓）の子窓でフリップモデルが使えるか分からない。HwndRenderTarget でも `NEAREST_NEIGHBOR` で描けて、絵が変わるときだけ描けば足りるはず。CPU・メモリを測って足りなければ替える
- **待ち時間は高精度の waitable timer に相対時間で渡す**: 高精度のタイマーが絶対時刻を受けるか自信がないため。ずれがたまらないよう、次の時刻は自分で足し算して持ち、今との差を渡す
- **省エネモードは `GUID_POWER_SAVING_STATUS`（バッテリー節約機能）で見る**: Windows 11 の新しい「省エネ」が同じ通知で来るかは to-fu で確かめる
- **まだ入れていないもの**: ほかの窓で全部隠れたときに止めること、バッテリーで止める設定、手での「表示を更新」（`WM_COPYDATA`）

## 2026-10-18 Mac で、ほかの窓に隠れたときに止まるか

- 測り方: pixwall の CPU 時間（`ps -o cputime`）が 30 秒でどれだけ増えるか。`top` の IDLEW（起きた回数）は `DispatchSourceTimer` では 0 のままで使えなかった

- 最大化した窓の後ろで動き続けるのは、本人の要望の「メニューバーの下まで描く」と「隠れているときは止める」がぶつかるところ。メニューバーと Dock のまわりだけが見えているときにも止めるかは本人に確認する（今は止めない）

## 2026-10-18 Mac で、最大化した窓の後ろでも止める

- 本人に確認して、メニューバーと Dock のまわりだけが見えているときも止めることにした
- **ほかの窓の位置を時々読む**: 窓を広げた・縮めたことはアクセシビリティの許可なしでは通知が来ない。許可を求めたくないので、`CGWindowListCopyWindowInfo` を時々読む
- **3 秒ごと**: 窓の一覧を 1 回読むと M1 で 4〜5ms かかった（`.optionOnScreenOnly`、窓 20 個）。1 秒ごとだとそれだけで約 0.5% になる。アプリの切り替えなどは通知ですぐ見るので、間隔は止まる・動き出すまでのずれにしか効かない
- **Dock に出るアプリの窓だけ数える**: 最初はすべての layer 0 の窓を数えたら、Mac の操作の道具（Cua Driver）の画面いっぱいの透明な窓で、いつも「覆われた」になって止まった。Stage Manager の飾りの窓も layer 0 にある。`NSRunningApplication(processIdentifier:)` を毎回呼ぶと 1 回 40ms 以上かかったので、Dock に出るアプリの pid の集まりを持ち、アプリの起動・終了のときだけ作り直す
- **見える部分が 5% 以下なら覆われたことにする**: macOS の窓のタイル表示（Fill）は、ふちに 8pt ほどのすき間を残す。1440×800 の画面で、すき間を足すと 3〜4% になる
- MacBook Air M1 で測ったこと（30 秒の CPU 時間。テストで残った設定の「画面を埋める・2倍」のまま）: 前の版 0.16〜0.19 秒、この版 0.20 秒。Terminal を Window > Fill で広げると 0.01 秒（止まった）。元の大きさに戻すと 0.20 秒（動き出した）。メモリ（phys_footprint）11MB

## 2026-10-18 Windows は DirectComposition の面の差し替えで出す

- **測り方を CPU のサイクル数に変えた**: `TotalProcessorTime`（タスクマネージャーの CPU 時間と同じ）は 15.6ms 刻みで数えるので、短い仕事を時々するだけの pixwall では、同じ版でも 30 秒で 0.03 秒から 0.6 秒までぶれた。`QueryProcessCycleTime` で 60 秒のサイクル数を数え、1 秒あたりの百万サイクル（Mcyc/s）で比べる。to-fu は 3.6GHz なので、36 Mcyc/s が 1 コアの 1%
- 比べた結果（64×64・30 フレーム・100ms、3440×1440 に「整数倍で最大」、to-fu）:
  - `ID2D1HwndRenderTarget` + `WS_EX_LAYERED`: 27〜29 Mcyc/s
  - 元の大きさのフリップモデルのスワップチェーンを DirectComposition で拡大: 23 Mcyc/s。ドライバーの裏のスレッドが 15 Mcyc/s、pixwall のスレッドは 6.5 Mcyc/s。`PREVENT_INTERNAL_THREADING_OPTIMIZATIONS` を付けると、ドライバーの仕事が pixwall のスレッドに移って合計 20.5 Mcyc/s
  - **フレームごとの面を差し替えて `Commit` だけ: 7.0 Mcyc/s（1 コアの約 0.19%）**。このうち 2.8 Mcyc/s は、1 枚だけの画像（何も描かない）でも動いている裏のスレッド。`Present` をやめると、描くたびのドライバーの仕事が無くなる
- メモリ: ワーキングセット 37MB、プライベート 55MB。目安の 30MB を超える。1 枚だけの画像でも同じくらいなので、大半は Direct3D とドライバー（NVIDIA）を読み込んだ分。目安をどうするかは本人に確認する
- dwm.exe: pixwall が無くても to-fu では 560〜730 Mcyc/s あり（ほかのアプリの分）、pixwall を動かしても止めても、違いはそのゆれの中に埋もれて見分けられなかった
- 確かめたこと: アイコンの後ろ（24H2 の並び）に出る。全体の色が入れ替わる GIF で、半透明のタスクバー越しに色が 250ms ごとに入れ替わるのを見た。ドットの端はぼけない。`taskkill`（`/f` なし）で終えると OS の壁紙に戻る
- まだ確かめていないこと: Explorer の作り直し、解像度・表示スケールの変更、複数の画面、アイコンを出した状態でクリックできるか（to-fu はデスクトップのアイコンを隠す設定）。本人が使っている最中の画面を動かさないよう、夜は触らなかった

## 2026-10-18 Windows のメモリは、作り終えたらワーキング セットを手放す

- 測り直すと、37MB だったワーキング セットのほとんどは、ほかのプロセスと分け合う DLL（NVIDIA のドライバーなど）のページだった。タスクマネージャーの「メモリ」に出るプライベート ワーキング セットは 11.6MB。Mac で測っていた phys_footprint もプロセスだけの量なので、目安とはこちらで比べるよう `SPEC.md` に書いた
- 外から `EmptyWorkingSet` で手放させると、30 秒後もワーキング セット 1.2MB・プライベート ワーキング セット 0.7MB で、ほとんど戻らなかった。起動時のドライバーの初期化で触っただけのページだった
- そこで窓を作り終えるたびに（起動・画面の変化・Explorer の作り直し）`SetProcessWorkingSetSize(-1, -1)` を呼ぶ。to-fu で 65 秒後にワーキング セット 3.6MB・プライベート ワーキング セット 1.4MB、CPU は 6.0 Mcyc/s で前と変わらない
- コミット（プライベート バイト）は 55MB のまま。ほとんどはドライバーが確保した分で、触らない限り物理メモリは使わない。GPU を使わない描き方（GDI など）は 24H2 の `Progman` の下では画面に出ないので、ここで止める

## 2026-10-18 Mac はフレームごとの layer を切り替えて出す

- 比べ方: MacBook Air M1、64×64・30 フレーム・100ms の GIF を「画面を埋める」2倍速（1 秒に 20 回描き替え）で、起動し直して 10 秒後から 60 秒の CPU 時間と footprint
- 前の版（1 つの layer の `contents` を差し替える）: 0.39〜0.40 秒、footprint 10〜11MB
- `sample` で見ると、仕事のほとんどは差し替えのたびの Core Animation の commit で、絵（IOSurface）を包み直して WindowServer へ送っていた。ほかの窓の位置を読む見張り（3 秒ごと）は 1 割ほど
- 試したこと:
  - フレームを先に IOSurface にし、タイマーを作り直さず使い回す: 0.39 秒で変わらなかった
  - **フレームごとの layer を最初に全部置き、`isHidden` を切り替える: 0.33〜0.35 秒（1 割強減った）**。IOSurface にしなくても同じだったので、`CGImage` のままにした。タイマーの使い回しは残した
  - 読み込みのあとに `malloc_zone_pressure_relief` を呼んでも footprint は変わらなかったのでやめた
- メモリ: footprint 11MB のうち、malloc が 5〜6MB（使っているのは 2.6MB で、残りは断片）、ライブラリの書き換え済みのページが 2MB ほど。Windows のように使わないページを手放す仕組みは macOS には無く（footprint は圧縮されたページも数える）、AppKit と SwiftUI を読み込むだけでこのくらいになる。目安の 30MB には十分収まるので、これ以上は追わない
- Windows との比べ: 1 回の描き替えあたり Mac 約 0.28ms、Windows（to-fu）約 0.17ms。1倍速で測り直すと、Mac は 60 秒で 0.21 秒（1 コアの約 0.35%）で、Windows（約 0.17%）の約 2 倍。footprint は 11MB で同じ

## 2026-10-19 画面を埋めるときの位置

- 余白×位置の端数は 0 の側へ切り捨てる。正の余白では前と同じ切り捨てで、負の余白（はみ出し）でも 0.5 のときに前の「半分にして切り捨て」と同じ位置になる
- 「整数倍で最大」は今も中央のまま。余白が上下と左右の両方にできることがあり、1つの値では動かす向きが決められない

- 時刻の切り替えが1分遅れた。タイマーは切り替わる時刻ちょうどに起きていたが、今の分を読む `time()` が粗い時計（`CLOCK_REALTIME_COARSE`）で数ミリ秒遅れ、まだ前の分を返していた。`clock_gettime(CLOCK_REALTIME)` で読む。cramgent で、足した時刻の 0.5 秒以内に替わることを確かめた

## 2026-11-09 Omarchy の壁紙に付いていく（Linux）

- 本人の要望（cramgent の別のセッション経由、本人の了承済みの設計）: Omarchy のテーマごとに GIF を決めたい・静止画と GIF を組にして Omarchy の壁紙のセレクターから選びたい。一番の条件は軽いこと
- Omarchy は選んだ壁紙を `~/.local/state/omarchy/current/background` のリンクで指す。セレクター（`omarchy-theme-bg-set`）もテーマの切り替え（`omarchy-theme-set`）も `ln -nsf` で付け替えるだけで、壁紙を替えたときのフックは無い。そこでリンクを見張る。`ln -nsf` は消して作り直す・入れ替えるので、リンクでなく親のフォルダーを inotify で見る。テーマを替えると `current/theme` が `rm -rf` と `mv` で入れ替わり、リンクの文字列が同じでも中身が替わるので、`theme` の変化でも選び直す。続けて来る知らせは 0.1 秒待って1回にまとめる
- 組の決め方は、静止画と同じフォルダーの下の `pixwall/` に同じ名前の GIF。Omarchy のセレクターは `find -maxdepth 1` なので下のフォルダーの GIF は一覧に出ず、静止画だけが並ぶ。テーマを替えるときは `cp -r` なので `pixwall/` も一緒に写る
- 組の無い静止画では、pixwall は面を消して描かない（Omarchy の Quickshell が静止画を描く）。二重に描かず、CPU も 0。GIF を直接選んだら pixwall が描く（本人の了承で OWE（owed）を止めたので二重にならない。OWE は GIF を動画にして流すのでドットが崩れていた）
- 並べ方を組ごとに持つ形は、画像のパスをキーにした `omarchySlots`。時刻・外観の切り替えと違い、組の数は Omarchy 側のファイルで決まるので、設定には変えたものだけを書く
- core の `SwitchBy` に `Omarchy` を足した。Windows・Mac の常駐側は `Resolved` が `mainSlot` を返すので切り替えない。Windows の設定画面（C#）と Mac（Swift）は知らない値を `none` として読む。CLI で `omarchy` を受けるのは Linux だけ
- cramgent で、本物の Omarchy と分けた場所（`XDG_STATE_HOME`・`XDG_CONFIG_HOME` を試験用に、別の D-Bus）で確かめた: リンクを組ありの静止画 → 描く、組なし → 0.6 秒以内に面が消える（PSS は 22MB のまま、CPU 0）、GIF を直接 → 描く
- cramgent の本物の Omarchy で確かめた（本人の了承のうえ、壁紙・テーマを替えて戻した）: `omarchy-theme-bg-set` で組なしの WebP → pixwall の面が消える（CPU 0 のまま）、組ありの静止画・GIF の直接 → 描く。`omarchy-theme-set` でライト・ダークを替えると、そのテーマの `pixwall/` の GIF に替わる。初めは、テーマを替えても組の GIF のパス（`current/theme/backgrounds/pixwall/…`）が同じなので読み直さず、前のテーマの GIF のままだった。ファイルの印を見て読み直すようにした
- ログイン時の起動は、uwsm が使う `systemd-xdg-autostart-generator` が `app-pixwall@autostart.service` を作り、`xdg-desktop-autostart.target` に入ることと、その単位を起こすと pixwall が動くことで確かめた。ログインし直すのは、GUI の中で別の作業（Claude のセッション）が動いていて落としてしまうので避けた。ディスクが暗号化されているので再起動もしない

## 2026-11-09 本物の GNOME で確かめる（画面の撮り方）

- 本人がこの PC の GNOME に入れたので、本物のデスクトップで確かめた。撮影は、GNOME Shell の `org.gnome.Shell.Screenshot` が GNOME 自身の撮影アプリ・ポータル以外からの呼び出しを断る（`AccessDenied: Screenshot is not allowed`）ので、xdg-desktop-portal の Screenshot を確かめの窓なしで呼ぶ（`linux/tests/portal_shot.py`）。初めての1回だけ GNOME が「許可しますか」を出し、本人が許可した（PermissionStore の `screenshot`）。ほかの窓を写さないよう、上の帯だけを切り出して見る
- 上のバーの裏に pixwall の絵が出ないのは、blur-my-shell のバーのぼかしが「静的」（GNOME の壁紙の写しをぼかす）だったため。本人の環境の blur-my-shell を「動的」（後ろをそのままぼかす）にすると、バーの裏が pixwall の絵（余白の色・GIF）になった。pixwall 側は何も変えていない
- 確かめたこと: 並べ方を変えるとすぐ変わる、ダーク・ライトで別の GIF にすぐ替わる、終了すると GNOME の壁紙に戻り、もう一度有効にすると戻る

- この PC は仮想マシンで、virtio-gpu に 3D が無い（`-virgl`）ので GNOME が CPU で描く。そのため pixwall が絵を替えるたびの描き直しが重く、64×64 の GIF を整数倍（1024×1024）で動かすと GNOME Shell の CPU が1コアの約 28% 増える（blur-my-shell のバーの動的なぼかしで、さらに約 9%）。拡張機能は絵の部分だけを描き直す作り（余白は固定の色の面、フレームは前もって GPU に置いてある）なので、拡張機能の側で大きく削れる所は無い。GPU のある機械（cramgent など）ではこうならない


## 2026-11-09 GNOME の壁紙にも1枚目を入れる

- 本人の考え: Mac・Windows と同じく GNOME の壁紙も今の GIF の1枚目にすれば、blur-my-shell のバーのぼかしを「動的」にしなくても、バーの裏が pixwall と同じ絵になる。そこで、未決事項にしていた「概観の中の壁紙も pixwall の絵にするか」を、入れる形に決めた

- 同じ名前の PNG を書き直すと GNOME が前の絵を使い続けることがあるので、a と b を交互に使う
- 拡張機能は、画面をロックすると止められ、ロックを解くと動かし直される（`session-modes` を書いていないため）。止めるたびに戻すと、ロック画面が元の壁紙になり、解くたびに描き直す。`Main.sessionMode.isLocked` のときは戻さず、描き直しも、覚え書きの key（画像の大きさ・更新時刻・並べ方・色・画面の大きさ・パス）が同じなら飛ばす。画面の無い GNOME Shell でロック → 戻さない、解く → 同じ PNG のまま、を確かめた
- 起動したばかりで設定を読む前に画面を数えたときは、まだ入れない（画像が無いと見て戻してしまい、そのあとすぐ入れ直すことになるため）
